The Challenge

A system that works today, but can't safely evolve

Meridian's inventory dashboard covers the core — inventory, orders, spending — but was left unfinished by the previous vendor. Three things stand in the way of moving forward:

Reports module defects

Eight or more logged issues: filter behavior, i18n gaps, inconsistent data patterns.

No automated tests

IT has been unwilling to approve changes without a safety net — effectively freezing the system.

Missing capability

Operations has no way to turn stock and demand data into a restocking decision.

Current State

What the handoff notes tell us — and don't

The previous vendor's documentation confirms the stack (Vue 3 + FastAPI, JSON-file data, no database) and the API surface. It's thin everywhere else.

"Reports module was in progress; not all filters wired up... some views still use older patterns — migration incomplete."

Our read

Thin documentation is itself a finding, not just an inconvenience. We won't price or plan against claims we haven't verified — which is why our engagement starts with an independent architecture review.

Our Approach

Stabilize first. Build second. Document throughout.

We sequence delivery around risk, not just the RFP's numbering. Automated testing (R3) is technically item three, but because it's what unblocks every future change, we build it in from Phase 2 onward rather than bolting it on at the end.

  • Verify the system independently before committing to scope or price
  • Fix root causes in Reports, not symptoms
  • Build Restocking on top of a proven test-coverage pattern
  • Leave Meridian with documentation IT can actually use
Phase 1 · Discovery

Architecture Review (R4)

We trace the real system — how data flows from the Vue frontend through the FastAPI backend to the JSON data layer — and verify what the handoff notes could not confirm.

  • Independently validate the current-state assumptions before pricing Phases 2–4
  • Produce the current-state architecture document as a byproduct of this review, not a late add-on
  • Use findings to confirm or adjust the Phase 2–3 estimate with Meridian
Phase 2 · Stabilize

Reports Remediation + First Test Suite (R1 + R3)

Required

Each of the 8+ logged Reports defects is root-caused individually — including finishing the stalled Options API → Composition API migration where it's the actual cause.

Why testing starts here

Every Reports fix ships with an automated test. This gives Meridian's IT team a working example of test coverage before we build the larger Restocking feature in Phase 3.

Phase 3 · Build

Restocking Recommendations (R2)

The engagement's centerpiece — and the feature Meridian's operations team asked for directly. Stock levels, demand forecast, and a budget ceiling become an actionable purchase order recommendation.

Zero/negative stock

Handled explicitly, not assumed away.

Budget below minimum order

Recommendations degrade sensibly, not silently.

Cross-warehouse conflicts

SF, London, and Tokyo have different lead times and demand.

Phase 4 · Document & Handoff

Finalized Architecture Docs (R4)

Because most of this documentation is produced during Phase 1 and kept current through Phases 2–3, Phase 4 is a short finalization and handoff step — not a from-scratch writing exercise at the end of the engagement.

  • Formal handoff session with Meridian IT
  • Sign-off on documentation and the automated test suite
  • Clear ownership model for future changes
