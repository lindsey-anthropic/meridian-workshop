State & Data Flow

No Pinia/Vuex. State lives in module-scope singleton composables (shared refs, imported wherever needed):

  • composables/useFilters.js — the 4 shared filters (Time Period, Warehouse, Category, Order Status), rendered once by components/FilterBar.vue in the global app shell.
  • composables/useI18n.js — locale state + translator, backed by locales/en.js / locales/ja.js.
  • composables/useAuth.js — mock current-user session state.
  • utils/currency.js — plain formatting helpers (USD/JPY), not a composable.

Views fetch their own data in onMounted and re-fetch via a watch on the shared filter refs — there's no central store or caching layer beyond the one-time JSON load on the backend.

API Client

client/src/api.js — axios-based, single exported object, ~18 methods, base URL hardcoded to http://localhost:8001/api. Builds query params from active filters, skipping 'all'.

Divergence: Reports.vue calls axios directly instead of going through api.js, uses the legacy Options API instead of Composition API, and doesn't consume useFilters or useI18n at all — it's the one view that grew apart from the rest of the app's conventions. Directly relevant to the Reports defects in scope for this engagement.

i18n Coverage

Locale dictionaries (en.js/ja.js) and useI18n are wired into App.vue, FilterBar.vue, and the Dashboard/Inventory/Orders/Demand/Spending views. Reports.vue and Backlog.vue are hardcoded English with no translation calls.

Styling

No CSS framework. Global tokens and base component styles (cards, badges, tables, nav) live in an unscoped <style> block in App.vue — the de facto design system. Colors are hardcoded hex values, not CSS variables.

Filtering Logic

Shared helpers apply_filters() and filter_by_month() are defined once and reused by inventory/orders/dashboard-summary. The two /api/reports/* endpoints implement their own separate hardcoded aggregation rather than reusing these helpers — a second divergence point that lines up with the frontend's Reports.vue divergence.

Models & Validation

Pydantic v2, all models defined inline in main.py: InventoryItem, Order, DemandForecast, BacklogItem, PurchaseOrder, CreatePurchaseOrderRequest. Used as response_model on inventory/orders/demand/backlog; spending and reports endpoints return raw dicts with no schema enforcement.

Test Coverage

Exists Backend

pytest + FastAPI TestClient, 40 tests across tests/backend/: inventory (list/filter/404/shape), dashboard (filter combinations, calculations), and misc endpoints (demand, backlog, spending, root).

Missing Frontend / E2E

No browser-level test infrastructure exists at all — no Playwright/Cypress config, no e2e directory. This is the gap R3 of the engagement addresses.

Notes for Incoming Work

  • Reports.vue is the outlier on both tiers — legacy Options API, direct axios calls, no shared filters, no i18n on the frontend; separate hardcoded aggregation on the backend. This explains the defect cluster reported in R1 and narrows where to look first.
  • Backlog.vue is orphaned — built but not routed. Worth confirming with Meridian whether it should be wired in, merged into Dashboard (which already has an inline backlog table), or removed.
  • No database — all data is flat JSON loaded once at process start. Any feature needing to persist new data (e.g., purchase orders for a Restocking feature) needs a real write path; today's purchase_orders.json is an empty placeholder with no create/persist logic wired up server-side beyond the endpoint stub.
  • No CSS variables despite a repo convention note recommending them — colors are repeated hardcoded hex values across files, worth consolidating before any visual refresh (D1).
