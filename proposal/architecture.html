3 Request / response flow

The intended data path is uniform across the application — except where the Reports module diverges from it (§6):

  1. A view loads and reads the active filters from the useFilters composable (Time Period, Warehouse, Category, Order Status).
  2. It calls a method on the central api.js client, which serializes filters into query parameters.
  3. axios issues an HTTP GET to the FastAPI backend on port 8001.
  4. FastAPI applies apply_filters() / filter_by_month() against the in-memory data and validates the result through Pydantic models.
  5. JSON returns to the view, where raw data is held in refs and derived values in computed properties for rendering.

5 Data layer

Data lives as JSON in server/data/, loaded into memory at startup by mock_data.py. Writes do not persist — restarting the server reloads from file. Suitable for the current scale (<10K items) but with no concurrency, indexing, or durability guarantees.

6 Current-state findings & deviations

The review surfaced the following. Each is mapped to the relevant scope item. Together they confirm the core theme: the system is sound in shape but inconsistent in execution, and unverifiable.

Reports module is built to a different standardR1
Reports uses the legacy Options API, calls the backend directly with a hard-coded URL (bypassing api.js), emits console.log on mount and on every render, has no filter bar, and uses hand-rolled (non-localized) number/currency formatting. Every other view follows the shared pattern.
i18n scaffolding exists but is not applied everywhereR1 · D2
A useI18n composable, en/ja locale files, and a LanguageSwitcher are present — but modules such as Reports do not use them. The foundation for the Tokyo team's i18n need (D2) is already in place; it simply was not extended.
Frontend calls write endpoints the backend does not implementR2
api.js defines createPurchaseOrder, getPurchaseOrderByBacklogItem, and task CRUD methods (getTasks/createTask/deleteTask/toggleTask), but the backend exposes no /api/purchase-orders or /api/tasks routes. These are client stubs ahead of unbuilt server work — directly relevant to building R2's purchase-order flow.
Orphaned view: BacklogR1
Backlog.vue exists as a full page but is not registered in the router (main.js) and not linked in the navigation. It is reachable only indirectly via a detail modal. Either an incomplete feature or dead code — to be confirmed with Meridian.
No automated test coverageR3
There are no end-to-end or unit tests in the project. This is the root cause of the change freeze: no change can be verified before release. Addressed first in our plan so subsequent work lands safely.
Incomplete Options API → Composition API migrationR1
The project standard (per the codebase's own guidance) is the Composition API, but Reports — and potentially other areas — remain on the Options API. Inconsistent patterns raise the cost of maintenance and of the remediation itself.
Production hardening deferred (expected for current stage)future
No authentication, CORS open to all origins, no rate limiting, no input validation beyond type checks, and a non-durable data layer. Acceptable for an internal tool at this stage; flagged here so Meridian IT can plan for it. A database migration is a reasonable future recommendation but is out of current required scope.
