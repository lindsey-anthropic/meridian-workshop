System Overview

The application is a two-tier system: a Vue 3 single-page frontend and a Python FastAPI backend, with no database — all data is loaded from static JSON files into memory at server startup. There is no authentication layer; the system is intended for internal, trusted-network use only.

Frontend Structure

views/

One component per route: Dashboard, Inventory, Orders, Demand, Spending, Reports.

  • All migrated to Composition API as of this engagement (Reports was the last holdout)

composables/

Shared reactive state, singleton-style.

  • useFilters — global Time Period / Warehouse / Category / Status filter state, read by the top-level FilterBar and by each view
  • useI18n — translation lookup + locale switching
  • useAuth — mock current-user data only

api.js

Centralized API client — the intended single point of contact with the backend for every view.

  • All endpoints now routed through here, including Reports (previously bypassed it directly with axios)

Backend Structure

server/main.py defines all REST endpoints directly against in-memory data loaded by mock_data.py. Common filtering logic (apply_filters, filter_by_month) is centralized and reused by most endpoints — the Reports endpoints were the exception until this engagement.

Findings from Discovery

Independent verification surfaced items the previous vendor's handoff notes didn't mention. Resolved items are marked; open items are flagged for follow-up.

Resolved Reports page ignored the global filter bar

Reports.vue never read shared filter state and the backend endpoints accepted no filter parameters at all, so changing Warehouse/Period/Category/Status had no effect on the Reports page. Fixed as part of R1: both frontend and backend now follow the same filtering pattern used everywhere else.

Resolved Reports page was the last Options-API holdout

Confirmed the handoff note "migration incomplete" — Reports.vue was the only view still on the Options API, bypassing the shared API client and i18n system, with unremoved debug logging. Migrated to Composition API as part of R1.

Open views/Backlog.vue is not registered as a route

The file exists but isn't wired into main.js's router — it appears to be an abandoned or in-progress feature, distinct from the BacklogDetailModal used on the Dashboard. Recommend confirming with Meridian whether this was intentional before removing or completing it.

Open Dashboard references an unregistered PurchaseOrderModal component

Dashboard.vue's template uses <PurchaseOrderModal>, but no such component is imported or registered, and no matching file exists in components/. The "Create PO" action likely fails silently. Flagged for remediation alongside R2 (Restocking), since purchase-order creation is directly related.

Open No authentication or session management

useAuth hardcodes a single mock user; there is no login flow, token handling, or access control. Acceptable for the current internal/demo deployment, but worth flagging to Meridian IT as a gap if the system is exposed beyond a trusted network.

Info No database — static JSON, in-memory only

All data resets on server restart. Fine for the current scope; worth a conversation with Meridian if data volume or persistence needs grow (see open question on SKU/order scale raised in our technical approach).

Recommendations Going Forward

  • Continue routing all new frontend data access through api.js — no direct axios calls from views.
  • Extend automated test coverage (R3) to lock in the Reports fix and prevent similar regressions.
  • Resolve the two open findings above (orphaned route, missing modal) alongside R2, since both touch purchase-order and backlog workflows.
